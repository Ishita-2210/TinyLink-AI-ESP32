# Physical validation procedure

This procedure remains **unexecuted** until a board is connected. Record the actual board marking and esptool chip identification before choosing/uploading a target. A classic ESP32 DevKit uses the supplied `esp32dev` target. C3/S3/C6 boards need a matching board configuration; do not assume pin or flash compatibility.

1. Use a data-capable USB cable. Run `python -m host.collect --list-ports`, unplug/replug if needed, and identify the USB port. Bluetooth COM ports are not ESP32 evidence.
2. Put laptop and board on the same permitted LAN (classic ESP32 requires 2.4 GHz). Disable guest/client isolation or use a private network that allows peer communication. Note the laptop IPv4 from `ipconfig`. Keep the laptop awake.
3. Copy `firmware/include/secrets.example.h` to ignored `firmware/include/secrets.h`. Set SSID, password, laptop IPv4 octets and port. Never commit that file. The default credential-free build intentionally emits `config_error` and never associates.
4. Start `python -m host.endpoint --bind 0.0.0.0 --port 3333`. If Windows requests a firewall choice, allow Python on your trusted private network. Do not disable the firewall. Both board and laptop may be Wi-Fi clients; laptop Wi-Fi scheduling contributes to the measured RTT.
5. Build and upload: `python -m platformio run --project-dir firmware -e esp32dev --target upload --upload-port COM9` (replace COM9 with the identified port). Some boards require holding BOOT during the initial upload connection.
6. Collect at least five minutes per condition: `python -m host.collect --port COM9 --duration 300 --output data/sessions/normal-01.jsonl`. Close other serial monitors first. Opening serial can reset a DevKit; ten slots of warmup are expected. Inspect `features_valid`, counters and `model_id`.
7. Repeat separate sessions for normal service, naturally weaker signal, endpoint stop/restart, and a temporary outage of an AP you own or may test. Do not interfere with third-party networks. Endpoint unavailability should increase failure rate while Wi-Fi association may remain connected. AP outage should show disconnect/recovering states, retries and eventual recovery after service returns. Retries: 10 s association deadline, 1/2/4/8/16 s backoffs, then a 60 s cooldown after six failures; repeat bursts indefinitely. Actual timing awaits measurement.
8. Verify the serial collector keeps writing during outages, rejects boot noise and resumes after unplug/replug. Its five serial-open/read failure limit is intentional; restart with a fresh output file after exhaustion. Review `.stats.json` for rejects, gaps, resets and failures.
9. Run `python -m host.benchmark --input data/sessions/normal-01.jsonl` for min/median/p95/max observed firmware inference/extraction timing. Capture enough valid windows across all states. A zero-microsecond duration is below timer resolution, not a zero-cost operation. Record firmware build size with `python -m platformio run --project-dir firmware` and the exact toolchain/configuration. Configured SSID/password change the built image; the documented size is the credential-free image.
10. Gather >=6 independent real sessions (prefer many more). Concatenate whole files in acquisition order, preserving `session_id`; train into a separate candidate output/header before replacing the shipped synthetic model. Compare held-out real results and the policy/majority baselines. Report current-window policy approximation explicitly. Update README/results only with evidence.

The pipeline cannot distinguish interference from laptop CPU scheduling, endpoint failure, RF fading or AP congestion. The probe failure rate is endpoint reachability over scheduled slots, not a network-wide packet loss estimate. These limitations apply even after successful hardware tests.
